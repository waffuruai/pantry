# wpantry CLI contract

Status: frozen at schema 1, 2026-10-25. Owner: Eric.

The command line, its exit codes, its JSON and its cache file are wpantry's only stable surface. Callers (ops, Syrup, wsentinel, agents) depend on this page and nothing else. The product is Pantry, and its command is `wpantry` (how it is built: [docs/public/architecture.md](../docs/public/architecture.md)). It MUST pass the contract tests, which run the binary and check its output rather than its internals.

## Change rule

- Additive changes only: a new subcommand, flag, JSON key, finding `kind`, `vuln_id` value or cache column is fine without a bump.
- Removing or renaming a JSON key, changing a key's type, or changing what an exit code means bumps `schema`. The cache schema follows the same rule.
- `version --json` and every JSON envelope carry `schema`, so a caller can refuse an output it doesn't understand.

## Programs that drive wpantry

These outputs are stable for a program that runs wpantry and reads its JSON, under the change rule above.

- `report all --json` has two additive fields. `scan` is the latest scan row, even when it predates the history window. `fix_plan` is the same list of IDs and fix steps as `fix list --json`, read in the same cache transaction as the findings. Exposure rows in JSON history also carry a stable finding id.
- `fix F-… --from-scan ID` requires a positive latest scan ID and one unattended finding from that scan. A changed scan or missing automatic fix is an error before a command runs, and so is a committed secret or an id that matches more than one finding of that scan (`This finding has no automatic fix in the selected scan.`). Use `--dry-run` to show the update and `--yes --no-input` to run an approved update. Without `--yes` or `--dry-run`, `--from-scan` with `--no-input` (or with no terminal on stdin) is a usage error, exit 2, and nothing runs; at a terminal it asks first. Changed 2026-11-21: `--no-input` alone ran the fix. With `--dry-run --json` it prints one object, `{schema, scan, command}`: the schema (1), the scan ID and the one command the fix would run.
- Applied targeted fixes record their source scan. The history records a verification scan only after a later complete scan of the same scope confirms the finding is resolved.
- `schedule status --json` returns `schema`, `backend` (`launchd`, `systemd`, `cron` or `windows`), `installed`, `enabled` (null when absent, or when the scheduler could not be asked: an unavailable `launchctl` or `systemctl` is unknown, never a failed status; on macOS it is the same `launchctl print` answer as `loaded`. Changed 2026-11-25), `loaded` (macOS: true while `launchctl print gui/<uid>/ai.waffuru.wpantry` lists the job, even when its plist is gone, as after an uninstall whose `bootout` failed; false when it does not; null when launchctl could not be asked and on other systems. Added 2026-11-21), `interval` (human-readable, null if unknown), `every`, `at`, `last_run` (UTC, null before a readable result) and `program` (the executable path the registered job runs, read from the job itself: the plist's first `ProgramArguments` entry, the `ExecStart` of `wpantry.service`, the crontab line's command or the task's `Command`, which is `wpantry-desktop.exe` (or, on macOS and Linux, `wpantry-desktop`) when the job runs the launcher; null when nothing is scheduled or it cannot be read. It can name a file that no longer exists, or a different `wpantry` from the one asked. Added 2026-11-23). Windows installs a least-privilege, per-user Task Scheduler job, runs it while that user is signed in and accepts the same intervals. When a windowless launcher, `wpantry-desktop.exe`, sits beside `wpantry.exe`, the task runs `wpantry-desktop.exe --scheduled-run`, which starts the scanner's `schedule run` with no console window, waits, and exits with its code. Without one the task runs `wpantry.exe schedule run`. Changed 2026-11-21. On Windows and with cron the job is found by exact name only: the task whose full name in `schtasks /query /fo csv` is `\Waffuru-Pantry-<SID>` (a task whose name only starts with that, or sits in a subfolder, is another task), and the crontab line that ends with ` # wpantry schedule` as its own word (a line that only contains that text is the user's). `status` never reads, and `install` and `uninstall` never change or remove, any other task or line. Changed 2026-11-25. launchd, systemd and cron follow the same rule: when an executable `wpantry-desktop` (a regular file or a link to one, with an execute bit) sits beside the scanner, or beside the file a `wpantry` link points at, `schedule install` writes the plist's `ProgramArguments`, the `ExecStart` of `wpantry.service` and the cron line to run `wpantry-desktop --scheduled-run` instead of `wpantry schedule run`; the label, timer, calendar, cron mark, `PATH`, priority and log paths are the same either way, and `program` reports the launcher. The launcher is a program a caller ships beside the scanner to run the scheduled scan on its behalf; it is expected to do its own work and call the scanner as it sees fit (`schedule run` is unchanged). The scheduler passes it `--scheduled-run` and nothing else, with the environment that scheduler gives any job: on launchd and systemd the `PATH` `schedule install` saw, and its output appended to `launchd.log` or `systemd.log` in the state folder; under cron cron's own environment, at `nice -n 10`, its output appended to `cron.log`. Its exit code means nothing to wpantry: nothing reads it, and the job's result is the launcher's business (systemd shows a nonzero exit as a failed unit). Running `schedule install` again rewrites the job to match what is beside the scanner then, so a caller that adds or removes the launcher migrates an existing job by saving the same schedule again. If the launcher is removed later without a re-install, the job keeps naming it: `status` still reads the job and `program` is the launcher's path, a file that no longer exists, until `install` runs again; `uninstall` removes the job whichever program it names. Without a launcher nothing changes. Added 2026-11-25. `schedule install` on every backend, Windows included, prints what the job runs from the same launcher lookup it registers with (and `--dry-run` prints the job that lookup gives): `It runs <launcher> --scheduled-run, the launcher beside the scanner.` when it runs the launcher, else that it runs `wpantry sync`, then `wpantry scan`. Changed 2026-11-25.
- `update --check --json` returns `current`, `latest`, `available` and release `assets` (a list of filenames or null for an older cache entry), plus `checked_at` (when that release information was fetched, `YYYY-MM-DD HH:MM UTC`, null when unknown) and `stale` (true when `--offline` answered from a cached copy older than its refresh age, a day by default, or dated in the future). Online it asks GitHub every time and replaces the cached copy, so its answer is fresh (`stale: false`) or, when GitHub can't be reached, an error (exit 3), never the old copy. A stale `available: false` means "not known to be newer", not "up to date". It exits 10 when an update is available, 0 when up to date or the answer is stale and not newer, and reports an error when there is no release information. `checked_at` and `stale` added 2026-11-21. The text form `update --check` says the same: for a stale answer that is not newer it prints `wpantry <version>: couldn't check for a newer release just now (last checked <checked_at>)` and exits 0, never "is the latest release"; a stale answer that is newer adds a line saying it is from the last check; online with GitHub unreachable it prints `wpantry <version>: couldn't check for a newer release (<why>)` and exits 0. Changed 2026-11-21. Changed 2026-11-23: online answered from the day's cached copy, or from an older one when GitHub couldn't be reached.

## Synopsis

```
wpantry [-h] [-V]
wpantry scan [--path DIR]... [--no-machine] [--refresh] [--offline] [--txt|--json|--jsonl|--csv|--md|--html] [-o FILE] [--since DAYS] [--no-input] [--jobs N]
             [--secret-rules FILE] [--licenses [FILE]] [--install-scripts FILE] [--no-posture] [--posture-policy FILE]
             [--repo-hooks FILE] [--suspect-policy FILE] [--hooks-policy FILE] [--no-malware] [--deep]
             [--no-online-hash] [--sources FILE] [--no-personal-files] [--allow-sleep] [--events]
wpantry fix [list|all|ID] [--dry-run] [--yes] [--undo] [--bundle FILE] [--hours N] [the scan's options]
wpantry search QUERY [--applicable] [--limit N] [--json]
wpantry report [findings|history|exposure|remediation|audit|summary|all] [--txt|--json|--jsonl|--csv|--md|--html] [-o FILE] [--since DAYS]
wpantry breach [--enable | --disable]
wpantry watch [--offline] [--json]
wpantry version [--json]
wpantry tools [--json]
wpantry skill
wpantry licenses
wpantry sync [--refresh] [--json]
wpantry schedule install [--every PERIOD] [--at HH:MM] [--dry-run]
wpantry schedule {status,uninstall,run}
wpantry cache prune [--older-than DAYS]
wpantry update [--check] [--yes] [--no-input] [--offline] [--version VER]
wpantry rules [--update] [--json]
wpantry rules gen SAMPLE... [--category CAT] [--family NAME] [--name RULE] [-o FILE]
wpantry rules goodware
wpantry sources [--json] [--sources FILE]
wpantry ignore add FINDING_ID [--scope user|repo] [--reason TEXT] [--all-places] [--no-input] [--json]
wpantry ignore list [--path DIR] [--json]
wpantry ignore remove ID [--path DIR] [--no-input] [--json]
wpantry help [COMMAND...]
```

`wpantry` with no arguments, `wpantry -h`, `wpantry --help` and `wpantry help` print the top-level help (`Usage: wpantry [options] [command]`, every command, the exit codes) and exit 0; nothing is scanned. `wpantry help COMMAND...` is `wpantry COMMAND... --help`; `wpantry -V` and `--version` print `wpantry <version>`. The command line is declared with [`wcli`](https://github.com/waffuruai/wcli), which generates the help and the errors: each command and option has one name, options are spelled out in full (no prefixes), an option's value is the next word or follows `=`, and `--` ends the options. A usage error prints `Usage: …` and `error: …` to stderr, with `(Did you mean …?)` when a command or option name is close, and exits 2.

Removed 2026-11-05, with no compatibility kept (nothing depends on wpantry yet): the second names `check` (for `scan`), `export` (for `report`) and `mitigate` (for `fix`); `scan --fix`, `--update` and `--dryrun` (`fix` and `fix --dry-run`); options with no command (`wpantry --json`); `--license` (`--licenses`), `--remove` (`--undo`), `--dryrun` (`--dry-run`); and abbreviated options (`--no-m`).

Removed 2026-11-05: wpantry scans files and never touches the clipboard. The `clipboard` command (the self-test and `--watch`, the resident guard), `scan --no-clipboard`, `schedule install --clipboard-guard` and `WPANTRY_CLIPBOARD_FAKE` are gone, and no finding is `CLIPPER-ACTIVE`; `CLIPPER-PERSISTENCE` and `CLIPPER-EXTENSION` are unchanged. Watching the clipboard live belongs to a resident watchdog. No compatibility was kept: nothing depends on wpantry yet.

|---|---|
| `scan` | Scan, report, and exit by the result; change nothing. The rows below, down to `search`, are its options and `fix`'s |
| `fix` | `scan`, then the unattended fixes, then every stopgap wpantry has that is for this host (asked on a terminal, skipped without one unless `--yes`; see `fix list`, `fix ID`), then a re-check whose result is the exit. On a terminal (stdin) without `--no-input`, list the fixes and ask `Run these N updates now? [Y/n]` first; declining changes nothing (exit as the scan). Added 2026-11-02, replacing `check --fix` |
| `--path DIR` | Repeatable (one directory each). The repo checks cover only the git repos at or under each DIR; a DIR holding no repo is scanned as one project without the git-history checks. A missing DIR is skipped with a one-line note on stderr. Without it the scope is every git repo under `$HOME`. With it, no other file of the user's is read: not `~/Downloads`, `~/Desktop`, `~/Documents` or the temp directories, for documents or malware; the machine inventory (and what persists) still runs unless `--no-machine`, and the HTML scope records `personal_files: false`. Changed 2026-11-20 |
| `--no-machine` | Skip the machine inventory (tools, runtimes, packages, apps, browsers, OS, Homebrew, editors, harness configs, running containers, CA trust, breach). Repo checks only |
| `--yes` | `fix` only: run the unattended fixes and write the stopgaps without asking. Added 2026-11-02 |
| `--dry-run` | `fix` only: print the update plan; change nothing |
| `--refresh` | Ignore cached answers |
| `--offline` | Cache only; anything never cached is `unchecked` |
| `--txt`, `--json`, `--jsonl`, `--csv`, `--md`, `--html`, `-o FILE`, `--since DAYS` | The report options, the same as `report`'s (below): when the scan is done it shows its findings exactly as `wpantry report` with the same options would. At most one format; `-o FILE` writes it there (a terminal report becomes `--txt`, `-o -` is stdout) and is checked before the scan: a directory or a missing parent fails with 3 before anything is scanned. Changed 2026-11-05: `--html FILE` was an extra file beside the terminal report; it is now `--html -o FILE` |
| `--json` | Print the envelope below instead of the terminal report; never prompts, and nothing else goes to stdout (the same for `--jsonl`, `--csv`, `--md` and `--html` without `-o`) |
| `--no-input` | Never prompt: the breach-consent question is skipped, and `fix` runs without asking. Prompts are only asked when stdin is a terminal: `? Question [y/N]` on stderr, Enter takes the default, anything but y/yes/n/no asks again |
| `--licenses [FILE]` | Also check repo dependencies' licenses, against FILE (`allow = [SPDX ids]`) or the bundled allowlist. Off by default (it's noisy): without it there are no `license` findings and `unknown_licenses` is 0. A missing FILE is a usage error |
| `--secret-rules` | Secret rules of your own, YARA (pantry-rules' form), added to the bundled ones; default `secrets.yar` in `$XDG_CONFIG_HOME/wpantry`. A rule that doesn't compile is a usage error (Changed 2026-11-07: replaces `--gitleaks-config`) |
| `--install-scripts`, `--repo-hooks`, `--suspect-policy`, `--hooks-policy` | Policy files, TOML; default to the user's own of the same name in `$XDG_CONFIG_HOME/wpantry/` (`~/.config/wpantry/`: `gitleaks.toml`, `licenses.toml`, `install-scripts.toml`, `repo-hooks.toml`, `posture.toml`, `suspect.toml`, `hooks.toml`), else the bundled ones (`assets/defaults/*.toml`): `--install-scripts` `allow = ["name@range"]`, `--repo-hooks` `files`, `packages`, `hosts`, `sha256`, `--suspect-policy` `ids`, `paths`. A missing named file, or a file that isn't TOML (named or found), is a usage error. Changed 2026-11-06: they were one entry a line, and only an option could name one. A repo's own `.gitleaks.toml` is reported (`REPO-POLICY`, warn), never obeyed |
| `--hooks-policy FILE` | Repo hooks someone has read and accepts: `hooks = [{ file = "…", when = "…", command = "…" }]` (one hook each, matched on its exact command, so a hook that changes what it runs is reported again) and `repos = ["path"]` (every hook that warns in the repos at or under that path). Only `OPEN-HOOK` and `INSTALL-HOOK` findings can be accepted; `RUNS-REPO-FILE`, `LOADER`, `IOC` and `MARKER` never are, and an entry naming one is refused in the finding's `fix_cmd`. Accepted hooks are not findings and are counted (`checked["repo hooks accepted by policy"]`); every `OPEN-HOOK` and `INSTALL-HOOK` `fix_cmd` ends with the `hooks` entry that accepts it. The file is part of the scan's scope |
| `--jobs N` | Repos scanned for secrets at once (default: half the cores, at most 4); each gets a share of the cores |
| `--no-posture`, `--posture-policy FILE` | The machine's own security settings (kind `posture`) run with the machine inventory; `--no-posture` skips them, the policy file lists check ids to skip (`skip = [ids]`, `POSTURE-` prefix optional). The ids are `POSTURE-<NAME>` as [posture.md](../docs/public/posture.md) lists them; `POSTURE-DNS-ENCRYPTED` (Medium: `warn`, never `fail`) was added 2026-11-01 |
| `--no-posture`, `--posture-policy FILE` | The machine's own security settings (kind `posture`) run with the machine inventory; `--no-posture` skips them, the policy file lists check ids to skip (`skip = [ids]`, `POSTURE-` prefix optional) |
| `--no-malware` | Skip the malware scan (kind `malware`): YARA rules over the top two levels of Downloads, Desktop and the temp directories, the programs launch items start, and the executables in the repos. Added 2026-11-04 |
| `--deep` | Everything in scope, slower. A machine scan reads every file of the computer this user can read, `~` first: on macOS the data volume's folders (`/Applications`, `/Library`, `/Users`, `/opt`, `/private`, `/usr/local`, …) and each local volume under `/Volumes`, never the read-only system volume; on Linux `/`, less `/proc`, `/sys`, `/dev`, `/run` and every network or pseudo mount; elsewhere `~`. Network shares are never read (32 levels, the repo walk's pruned directories skipped); with `--path` or `--no-machine`, every file under each DIR or repo. The malware scan reads those files with every system's rules, not only this system's and any system's. The secret scan reads them too (files up to 10 MB; bigger ones are not checked), as well as history: blobs up to 256 MB (10 MB otherwise; those over 10 MB one at a time) for up to six hours per repo (30 minutes otherwise). A secret history already reported isn't reported again from its file. Each file's result is kept while it's unchanged, so a second deep scan reads only what changed. A folder this user can't list is reported not checked, by place (on macOS, a terminal without Full Disk Access). Added 2026-11-04; changed 2026-11-20 and 2026-11-21 (every file for secrets, the whole computer) |
| `--no-personal-files` | On a machine scan, leave `~/Downloads`, `~/Desktop` and `~/Documents` out of the document and ClamAV pass and out of the malware scan's targets, before those folders are opened (on macOS, opening them can wait on a permission prompt); one `unchecked` finding, `Personal documents and images`, says so (on macOS a second, `Safari settings`, for Safari's protected app data). Both carry `excluded: true` and a note that starts `Skipped by your choice`: the user left that area out, no source failed, so they don't count in the scan's `unchecked` total and don't stop the scan resolving exposures or verifying fixes of its own scope. Changed 2026-11-21: they counted as failed sources, so such a scan resolved and verified nothing. The temp directories, what persists and the repos elsewhere are unchanged. On every scan, with or without `--no-machine`, the repo walk and every file walk also leave out those three folders: no repo under them is scanned, and a `--path` that holds them (such as `--path ~`) or a repo root that does (a home that is a git checkout) is read without them. A `--path` inside one (`--path ~/Documents/x`, or `--path ~/Documents` itself) is scanned as asked: the path the user names wins, and only that path and what is under it; the rest of the folder stays left out for every pass, the login programs and PATH lookups included (changed 2026-11-25: naming one project had lifted its whole folder). Changed 2026-11-21: a scan without the machine inventory, or with `--path`, still read them. No pass lists, opens or stats anything inside a left-out folder, and the exclusion is by path, before the folder is touched: the repo search, every walk (a link pointing into one is not followed), the programs that start at login (never read, signature-checked or malware-scanned when they sit inside one; each is reported as an `unchecked` finding that names the item and its program, and that one is a gap, not `excluded`, because nothing else speaks for it) and PATH lookups. On macOS the left-out folders are also `~/Pictures`, `~/Music`, `~/Movies`, `~/Library/Mobile Documents`, `~/Library/CloudStorage`, `~/Library/Mail`, `~/Library/Messages`, `~/Library/Safari`, `~/Library/Calendars`, `~/Library/Application Support/AddressBook`, `~/Library/Containers` and `~/Library/Group Containers`, the folders macOS guards with a prompt or a quiet denial. One more `unchecked` finding with `excluded: true`, `Repositories in personal folders`, and one `note` (`· left out of this scan (--no-personal-files): ~/Downloads, ~/Desktop, ~/Documents, ...; repos there are not scanned`) say what was left out, on every scan with the flag, the folders named whether or not they exist (checking would touch them). A folder the system refuses to list, here or anywhere in scope, is not checked: it is skipped quietly (a file walk lists it among the folders that could not be read, reported not checked by place), never retried and never a failed scan. Changed 2026-11-25: the repo search, links, login programs and PATH lookups could still open them, which raised a privacy prompt for a scan started by a GUI program or a scheduled job. A usage error with `--deep`, which reads everything under `$HOME`. The history scope of any scan with it includes `;no-personal-files` (changed 2026-11-21: machine scans only), so such a scan resolves no exposure a full one found, with one exception: a whole-machine scan (no `--path`) with it also resolves the open `machine:~` exposures it no longer lists, when it could have seen them. That is every exposure outside `~/Downloads`, `~/Desktop` and `~/Documents` (a path there, in any spelling the folders can be reached by, including another letter case on macOS and Windows and `..`, stays open for a scan that reads them), except Safari's protected-data check; an exposure with no path (`line 12`, none) closes only when it comes from the machine inventory (a formula, an app, a tool, a setting), never when it comes from a repo or a file. A full scan resolves the rest. Added 2026-11-25: the scheduled job's scope changed to `machine:~;no-personal-files` on macOS, which left what `machine:~` had recorded open for good. The HTML scope records `personal_files`. Added 2026-11-06 |
| `--no-online-hash` | Never look up a flagged file's SHA-256 online. Otherwise, after one yes (asked once on a terminal, kept in the cache as `online_hash_consent`), the SHA-256 of each file the malware scan flagged (at most 50 a scan), and nothing else about it, goes to YARAify and CIRCL hashlookup, and to MalwareBazaar when `ABUSECH_AUTH_KEY` is set. A malware verdict makes the finding `fail`, Critical, and its note names the source and family; a known-good answer is noted on a heuristic `warn`. A source that can't be reached is `unchecked`. Added 2026-11-04 |
| `--sources FILE` | The user's sources file for this run, in place of `~/.config/wpantry/sources.toml` (`$XDG_CONFIG_HOME/wpantry/sources.toml`), which is read when it exists (`specs/design/sources-file.md`). It may set a bundled source's `tier` (`default`, `deep`, `off`: an `off` source isn't asked, and what needs it is `unchecked`), and add sources of its own: YARA rules, hash, host and file-name lists, an OSV-compatible API (asked beside OSV.dev), or a hash lookup that sends only a SHA-256. A source of the user's whose host wpantry doesn't already ask, or that sends anything, is used only after a yes, asked once on a terminal and kept by its id and URL; without one it is `unchecked`. Each used is counted as `user source <id>`. A file that can't be used leaves the bundled sources in effect and is `unchecked`. Added 2026-11-05 |
| `--allow-sleep` | Let the machine idle-sleep during the scan. Otherwise, on macOS, the scan holds an idle-sleep assertion (`/usr/bin/caffeinate -i -w PID`) that ends with it; elsewhere nothing changes. `WPANTRY_ALLOW_SLEEP=1` does the same. Added 2026-11-06 |
| `--events` | `scan` only (not `fix`): while the scan runs, write its progress to stderr as JSON Lines ([below](#scan---events)). Stdout and the report are unchanged. No progress line, no prompts (as `--no-input`), no `WPANTRY_TIMINGS` lines; the notes the scan prints on stderr become `note` events. A caller detects support by `scan --help` listing `--events`; an older wpantry rejects it with exit 2 before scanning. Added 2026-11-24 |
| `rules` | The YARA rule sources the malware scan uses (ours, built in; YARA Forge's `full` package, fetched into `rules/` beside the cache at most daily; any `.yar` you put there), how many compile and how many are for this system; `--update` fetches YARA Forge now (exit 1 when it can't); `--json` as `{directory, sources: [{source, rules}], rules, this_system, rejected, update_failed}`. Added 2026-11-04 |
| `search` | Rank cached advisories (SQLite FTS5 syntax); `--applicable` keeps those in the latest findings |
| `report --jsonl` | Latest findings as JSON Lines, one object per finding: every [finding](#finding) key, with `aliases` (the record's other ids, joined with the finding's own), `url`, `record` (the full OSV JSON, or `null`), `first_seen`, `last_seen`, `resolved_at` (`YYYY-MM-DD HH:MM UTC` strings, `null` when unknown or open), `days_exposed`, `first_epss` and `first_epss_percentile` (the exposure's first EPSS score, `null` until it had one; added 2026-11-21) and `fix` (`null`, or `{attempted_at, mode, ok, verified, succeeded}` for the latest `fix` run of its `fix_cmd`). `report exposure --jsonl` (or `history`, `all`) adds the exposures a later scan of the same scope resolved and the latest scan no longer lists. `--csv` and `--jsonl` may be given together; one is required |
| `breach` | Show or set consent for the opt-in email breach check |
| `watch` | Ask OSV again (bypassing the daily cache) about every advisory the latest findings carry with `status == "warn"` and `fixed == ""`: the Critical, High and exploited-in-the-wild advisories no fix was released for. Prints each with `no fix yet` and its mitigation, or `FIX AVAILABLE: <component> <version>`; exits 10 when at least one has a fix now. `--offline` reads the cache only. `--json` prints `{"schema", "impl", "version", "watched": [{id, severity, summary, ecosystem, package, version, fixed (string or null), mitigation (string or null)}]}`. For an hourly cron: a non-zero exit is the signal |
| `version` | `{"version": "0.1.0", "impl": "rust", "schema": 1}` with `--json` |
| `tools` | The external tools this implementation runs, found or missing |
| `sources` | Every outside source (`assets/defaults/sources.toml`): kind, tier, host, licence, whether it is redistributed, when it was last fetched, whether that is fresh, and its last error; `--json` as `{sources: [{id, kind, format, tier, host, transport, user, license, redistribute, refresh_seconds, sends, last_attempt, last_success, fresh, error}]}` (times as epoch seconds, null when never); `--sources FILE` reads that user's sources file instead of `~/.config/wpantry/sources.toml`. Exit 0; 2 when the user's file can't be used. Added 2026-11-05 |

### Scope walk

The default scope walks `$HOME` to depth 6 without following symlinks and only looks at directory entries. A directory with a `.git` directory is a repo and is not descended into. A `.git` file (linked worktree, submodule) ends the descent and counts only when it is the `--path` itself. Pruned by name: `.git`, `node_modules`, `target`, `.build`, `vendor`, `.cache`, `dist`, `build`, `.venv`, `venv`, `__pycache__`, `.next`, `Library`, `.Trash`, `.rustup`, `.npm`, `.pnpm-store`, any `*.app`; by path: `go/pkg`, `.cargo/registry`, `.cargo/git`, `.local/share`. On macOS the default walk (no `--path`) also leaves out `~/Pictures`, `~/Music`, `~/Movies` and any `*.photoslibrary` or `*.musiclibrary` bundle: they hold no code projects and opening them raises a privacy prompt. A `--path` inside one is walked as asked. Added 2026-11-21. The count lands in `checked["git repos"]`.

## Platforms

macOS and Linux: everything. Windows (`x86_64-pc-windows-msvc`, from 0.5.0): the repo checks (`scan --no-machine`: lockfiles, secrets, install scripts, images, MCP servers), `search`, `report`, `version`, `tools`, `skill`, `licenses` and `breach`, with the same output as on Linux for the same repo. A machine scan on Windows reads the installed programs (`HKLM` and `HKCU` `...\CurrentVersion\Uninstall`, and the `WOW6432Node` view, with `reg query`, read only), counts them (`installed programs`), and checks the ones its reviewed program table names against CVE records; no other program's Publisher or name is sent anywhere. A record that applies is a finding of kind `app` with the CVE id as `vuln_id`; one that can't be asked or judged, including a DisplayVersion numbered another way than the record's versions, is `unchecked` (`installed programs against CVE records (...)`). It then reports one `unchecked` finding (`machine inventory on Windows`): winget, Scoop, Chocolatey, Windows Update and the certificate store aren't read yet. Changed 2026-11-18: installed programs were not read. Locations and `fix_cmd` paths are printed without the `\\?\` prefix that Windows `canonicalize` adds. `~` is `HOME`, else `USERPROFILE`; the cache default is `%LOCALAPPDATA%\wpantry\wpantry.db` when neither `XDG_CACHE_HOME` nor `HOME` is set. PATH is split as the platform does, and a tool name also matches its `.exe`, `.cmd` or `.bat`.

## `report --html`

The page shows the report the cache keeps for the latest scan: `scan --html -o FILE` and `report --html -o FILE` write the same page. It embeds the schema-1 envelope `scan --json` prints, the scan's scope (kept with the scan in the cache), the update plan and 14 days of history (`--since DAYS` for more), packed so a repeated string is stored once (`src/reporters/pack.rs`; the page unpacks it to exactly that JSON), and deflated as well when the packed bundle is over 1 MiB, which the page inflates with the browser's `DecompressionStream` (Chrome and Edge 103, Firefox 113, Safari 16.4 or later; an older browser shows a note pointing at `wpantry report --json`). ## `scan --events`

For a caller that runs the scanner as a child process (a script, a CI wrapper, an editor, a dashboard) and follows the scan while it runs. Added 2026-11-24.

- One JSON object per line on stderr, ending in `\n`, flushed per line. Plain printable ASCII (every other character is a `\uXXXX` escape), so no colour and no terminal control characters. Paths are absolute where the scan reads them (`at`, `start`) and as the report shows them in a finding (`component`, `location`).
- Every line has `v` (this format's version, 1) and `event`. A consumer ignores an event it doesn't know and a field it doesn't know: events and fields are added without changing `v`; `v` changes only when a field is removed or changes meaning. Separators may be `", "` and `": "`; read the lines as JSON.
- Before `start`: only a usage error (exit 2, as plain text: skip a line that isn't a JSON object). Argument parsing is the one step that runs before the first event, so it is the only failure that can leave a run without a `start`. Every later failure, a `-o FILE` that can't be written included (exit 3), is `start` and then `done` with `exit` and `error`. A reader that got no `start` knows the scan never began: it reads the exit code (2) and the plain text, and does not wait for a `done`. Changed 2026-11-25: an unwritable `-o` was plain text with exit 3 and no `start` or `done`.
- Order: `start` is first and `done` last, once each. The steps run in the order `start` lists them, each `begin` before its `end`, `index` up by one each time. `at`, `tally` and `finding` lines fall between a step's `begin` and `end`.
- Rate limits: `at` and `tally` are written at most every 100 ms (about 10 a second), and the `at` written is the newest path at that moment; the paths in between are dropped. `start`, `step` and `done` are never dropped.
- Backlog: a reader that falls behind does not make the scan hold more. At most 4096 `finding` and `note` lines, and 4 MiB of them, wait for the reader at a time; past either cap a new one is dropped and counted, never waited for. When the reader has caught up (and before the next `step` line, so inside the step it belongs to) one `dropped` event says how many were left out since the last one, and `done` carries the total. A consumer that must see every finding reads the report, which is authoritative and complete; a `step` end's `findings` and `unchecked` and a `tally` count what the scan found, dropped lines included. Added 2026-11-25 (additive: `v` stays 1).
- Heartbeat: inside a step, a stretch of 1 second with no line written gets a `tally` (the same counts again when none moved), so a step is never silent for much more than a second, whatever it is doing (a long read, a long look over a big tree, a slow lookup). Added 2026-11-24. Between steps nothing is written.
- A reader that closes its end early, or stops reading, never stalls or fails the scan: lines it can't take are dropped, and the exit code and stdout are those of the same scan read to the end. At the end the scan waits at most 5 seconds for the reader to take the lines still queued.
- A crash: an internal error that panicked is `done` with `exit` 3 and the panic's message in `error`: the first panic's, that is the worker's own text, not the generic one a thread that joined it adds after. The scanner's own panic message is not printed anywhere else, so once `done` has been taken, the same message is written as one plain line after it (`✗ wpantry: <message>`, on one line). That is the only text that follows `done`, and only after a crash: a reader treats `done` as the end of the stream and ignores anything after it. When the reader has not taken `done` within the 5 seconds, no line is written. Added 2026-11-25 (additive: `v` stays 1).

A finding's fix fields are the step `wpantry fix` would plan for that finding alone, and are left out when it has none: `fix_cmd` is the command or the manual steps the report's finding carries (its `fix_cmd`; for an update of mise, the instruction to update it by hand, as the plan says), `fix_auto` is whether `wpantry fix` runs it unattended, and `fix_provisional` is true when the plan made at the scan's end can replace it. The plan takes one command per component at the highest fixed version among all that component's findings, so a command from an early finding can upgrade to less than the final plan; and it joins every secret in one file into one script. So `fix_provisional` is true for a finding about a component version (anything but `unchecked` with a `version`) and for every `secret`, and false otherwise. Act on a provisional command only after `done`, from the plan (`wpantry fix list --json`, whose `scan` is `done.scan`); show the others (manual steps in a repo or a setting) at once. `fix_cmd` never holds a secret: like the report's, it names a secret's file and line and asks for the value, never shows it. Added 2026-11-25.

A `finding` event is provisional; the report is authoritative. An ignore file can still leave the finding out (in `rating`), and `severity` can be `""` or change there, where CVSS scores are filled in. What couldn't be checked comes as `finding` events with `kind: "unchecked"` and is counted apart. Events carry only what the report shows of a finding, never a file's contents: a secret's event names its rule, its file and its line number, never the secret or the text around it.

The steps, by `id`, with their titles. `start` lists only the ones this run takes.

| id | title | taken | its findings arrive |
|---|---|---|---|
| `sources` | Getting advisory data | always | as each source is asked (`unchecked` when one can't be) |
| `repos` | Finding repos | always | none (a missing `--path` is a `note`) |
| `machine` | Looking at this computer | without `--no-machine` | as each machine check finishes; an advisory after OSV answers for its batch |
| `dependencies` | Checking dependencies | always | as each lockfile's OSV answer is read, and the WordPress sites after theirs |
| `secrets` | Looking for secrets in git history | always | per repo, as its history scan is read (the scans run during `dependencies`; this step waits for them) |
| `repo-files` | Reading the repos' files | always | as each check finishes: hooks, hidden text, suspect code, MPTCP listeners, documents, install scripts |
| `images` | Checking container images | always | per image |
| `extensions` | Checking MCP servers and extensions | always | as each check finishes |
| `malicious` | Checking package names against known malicious packages | always | as each ecosystem is swept |
| `breach` | Checking email addresses against breaches | without `--no-machine` | by the step's end |
| `malware` | Scanning for malware | without `--no-malware` | by the step's end: a verdict waits for the hash lookups |
| `file-secrets` | Looking for secrets in files | `--deep` | at the step's end, with the files pass done |
| `rating` | Rating and saving the findings | always | none new |
| `report` | Writing the report | always | none |

The files pass, one read of each file for every content check and the malware scan, runs in the first step that needs it: `machine` on a machine scan, else `repo-files`. Its `at` lines name that step. Before it reads the first file it lists the folders not listed yet, looks over every file (its size and time) and looks each one up in the cache: those `at` lines have `kind: "dir"` (the folder of the file being looked over, then each root), and with a warm cache the pass may read no file at all. The `repos` step lists every repo's folders once (`at` lines with `kind: "dir"`, and `listed` growing).

A source that couldn't be reached is a finding with `kind == "unchecked"`, `status == "warn"`: never silence, never "clean". An area the user chose to skip is reported the same way with `excluded: true`; reports list it under "Skipped by your choice", apart from "Not checked".

What a repo's `.pantryignore` or the user's `ignore` file (`$XDG_CONFIG_HOME/wpantry/ignore`) skips is left out of `findings`, the cache and the history. `checked` counts it under `findings skipped by a repo's .pantryignore` and `findings skipped by your ignore file`, and the history files the secret scan didn't read under `files in git history skipped by a repo's .pantryignore`. ## `ignore --json`

Every envelope carries `schema` (1), `impl`, `version` and `action` (`add`, `list` or `remove`). The keys below are the whole object; a refusal prints the same envelope with `changed: false` and a `refused` object and exits 1.

`ignore add --json`, written:

```json
{"schema": 1, "impl": "rust", "version": "0.8.0", "action": "add", "changed": true,
 "finding": {"id": "F-3fa9c01b2e", "kind": "project", "component": "lodash", "location": "/home/u/app/package-lock.json", "vuln_id": "GHSA-xxxx-xxxx-xxxx"},
 "scope": "repo", "file": "/home/u/app/.pantryignore",
 "rules": [{"id": "R-5c1e0a9d44", "section": "project GHSA-xxxx-xxxx-xxxx", "pattern": "/package-lock.json", "place": "/home/u/app/package-lock.json"}],
 "reason": "not reachable", "all_places": false,
 "left_out": [{"id": "F-…", "why": "it is in another repo"}]}
```

Already ignored: `{schema, impl, version, action: "add", id, changed: false, already: true, scope, file}`. Refused: `{schema, impl, version, action, id, changed: false, refused: {code, message}}` (codes in the `ignore` row above). `reason` is `null` without one. `file` is the file's real path.

`ignore list --json`: `{schema, impl, version, action: "list", files: [{scope, file, exists, error}], rules: [Rule], removed_by_hand: [{id, scope, file, section, pattern, finding_id, added, reason}]}`, where a Rule is `{id, scope, file, line, section, active, pattern, source, finding_id, added, reason}`: `section` is `check` or `check id` (`null` before any header), `active` is false under a header the scan can't read (the rule applies to nothing), `source` is `command` for a rule `ignore add` wrote (then `finding_id`, `added` as `YYYY-MM-DD HH:MM UTC` and `reason` come from its comment, `null` when it has none) and `hand` otherwise (those three are `null`). `files[].error` is a message when a file can't be read (a repo's file that is a link), and the exit is 1.

`ignore remove --json`: `{schema, impl, version, action: "remove", id, changed, removed: [{id, scope, file, section, pattern, finding_id}]}` (`finding_id` is `null` for a rule written by hand); with nothing to take out because the log says it was added and the file no longer holds it, `{…, id, changed: false, already_gone: true}`, exit 0. Nothing matching is a refusal, `not-found`.
